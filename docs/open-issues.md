## 2. 数据风险

按「会不会丢数据」排序，前三条是必须让用户知道的。

**① 卸载扩展 = 删除全部数据。** 主库是扩展 origin 下的 IndexedDB，移除扩展时浏览器会连库一起删，没有回收站。装之前、删之前都请先导出备份。目前**没有自动备份**，也不打算在 v1a 做。

**② 换机器/换 profile，数据不跟过去。** 扩展 ID 变了，origin 就变了，库是另一个。唯一通路是导出 JSON 再恢复。新设备上库是空的，此时选「合并」等同完整导入（连设置与整理策略一起回来）；如果先手动建了分类再去恢复，就不算空库，设置会保持本机当前值。恢复时面板会提示「主库身份已切换」，旧环境还在写就会分叉——先把旧的那份停掉。

**③ 替换式恢复会清空当前主库。** 替换前会自动给当前主库拍一份完整快照，**拍快照、写副本、清库、写入是同一条事务**（`restoreWithSafety`）——快照拍完之后到提交之间没有别的标签页能插进来写，所以「刚显示保存成功的收藏被清掉、副本里也没有」这种两头空的情况不会发生；写库阶段失败则整条事务回滚，主库原样还在，也不会留下半份副本。副本同时写进本机库的 `meta`（不随替换清空），即便下载被拦、磁盘满、页面被关，回到「数据」页仍能看到「有一份替换前的安全备份还没确认保存」并重新保存；点「已确认保存」才会清掉这份临时副本。**只要这份副本还在，下一次替换会被直接挡下**（提示「还留着一份…尚未确认保存」），不会被新副本覆盖——包括「第二次替换本身失败」的情况，因为整份文件的校验排在事务之前。清理按副本编号核对，停在其他标签页的旧按钮不会误删刚存的副本。真正的风险只剩「两份都没了」时才会发生——所以替换后请确认为什么要替换，而不是把它当常规导入手段。

**④ 本地专用条目默认不进备份。** 不勾选「包含本地专用条目」，这些收藏就没了（它们本来就不该随文件走）。**同一条网址关联的待看也不会进**，三条路径都堵上了：从这条收藏「加入待看」新生成的、重新激活一条已完成待看的（会补写关联编号）、以及先独立加入待看再把同网址收藏设成本地专用的（导出时按网址再核对一次）。备份里会记下排除条数（`exclusions.readingForLocalOnly`），恢复端提示「排除过 N 条」。勾选等于把这些写进明文 JSON，自己权衡。

**⑤ 手机快照是明文。** 任何拿到 HTML 的人都能读到标题、链接、备注（如果开了备注开关）。设计上排除了本地专用与已删除条目，但**没有密码**，分享前先想清楚。

**⑥ 合并恢复不会复活本机已删的条目，也不会放宽本机的隐私范围。** 合并只新增本机没有的记录：本机已有的（包括已删除的、以及本机改过标题的）一律保留，不再按 `localRevision` 比大小——两台设备的写入次数本来就不能互相比较。判重同时看编号与网址：**同一网址、不同编号的备份收藏也绕不过本机的删除**（本机删过就跳过并计数，需要找回请到回收站单独恢复），墓碑是否生效按事务里的最终库状态判定，不会出现「在库里」又「已删除」并存。删除标记（墓碑）同样只认本机：一条收藏被设成「本地专用」再删除之后，合并一份它还是普通删除的旧备份，本机会保留 `local` 范围，不会让默认备份重新带上私密标题与网址（同网址不同编号的旧墓碑也一样；导出时还会拿墓碑的编号与网址再和本地专用条目核一遍）。代价是：**外部设备的修改不会被合并进来**，要那种效果只能用替换。恢复的是一份没有墓碑的旧备份时，界面仍会提示删除语义可能失效。

**⑦ 双设备同时写会分叉。** 没有同步机制，两台机器各写各的，只能靠备份合并。合并按 ID 与网址去重、保留本机版本，不会静默覆盖，但也**不解决「两边都改过同一条」的冲突**——它只会跳过并计数。

**⑧ AI 材料包是手动复制出去的。** 手动交接需要你自己把材料粘到外部 AI，粘出去的内容受对方隐私政策约束，扩展无法回收。材料包里已排除 `localOnly` 与 `aiBlocked` 条目，并只带白名单字段。校验通过到点「应用」之间如果改了整理策略或换了主库，应用会被拒绝：批次状态、主库身份与策略版本是在**同一条写事务里**复核的，中间没有可乘的窗口；界面会显示原因并解锁按钮，不会停在「应用中…」。

**⑨ 「彻底清空」是不可恢复的硬删除。** 为了让「清空后重新导入同一批书签」真的可行，清空会**连删除标记（墓碑）一起删**——只删记录的话，重新导入会全被判成「存在已删除收藏，未绕过墓碑」，用户看到的是「清空了却导不进来」。代价有三点：① 清空不走回收站，误点无法在本机还原，请先导出完整 JSON；② 墓碑没了，之后合并一份更早的备份时，这些条目会被当作「本机没有」重新带回（这正是墓碑原本要防的事）；③ 「全部收藏」页的清空会连同回收站里的记录一起清，分类页的清空只清该分类下的收藏、分类本身保留。撤销导入（按批次）不是清空：它只移除这一批新建的、之后没被改过的条目，改过的会保留并如实报数。

**⑩ 清空确认框的数量可能小于实际删除量。（2026-10-31 已修复，P9.0）** 原实现里分类页与未分类页的确认框按**当前活跃列表**计数（`items.length`），而 `purgeCategory()` 读取整张 `bookmarks` 表再按分类过滤，**连该分类下已进回收站的记录一起删**，相应的墓碑也一起清；确认框显示 120 条时实际可能删掉 130 条。

现在确认前会先查一次作用域明细（`purgeCounts` → `countPurgeAll` / `countPurgeCategory`），确认框改为「将删除 12 条记录（在库 11 · 回收站 1），并清掉 1 条删除标记」；点确认后再核对返回的实删数量，与确认时的总数不一致会明确提示而不是静默通过。证据：单测「分类清空把回收站里的记录算进来，计数与实删数量一致」「整库清空的计数包含回收站，且与实删数量一致」；`verify:p3`「清空确认框拆出在库 / 回收站 / 删除标记，且与实删数量一致」实测 `total=12 active=11 trashed=1 tombstones=1`，与主库一致。

**⑪ 撤回与清空没有清理快照。** 目前两者都是硬删，误操作只能靠**事先**导出的备份找回，本机没有留下"我刚才删了什么"的副本。批次撤回又必须硬删（要能立刻重导同一批书签），所以不能改成软删。**2026-10-31 P9.4 已落地（第一段）**：硬删前在同一事务里先写本机 `purgeSnapshots`（算候选 → 写快照 → 删除 → 记数），任一步失败整体回滚；数据页「最近清理」可预览并只找回这一次删掉的条目，冲突一律跳过不覆盖，不调用整库替换。边界：保留最近 5 份、单份 5000 条或 5 MB、总量 50 MB；**快照写不进去就一条都不删**。详见 [清理快照与单次清理恢复](purge-snapshot-and-restore-design.md)。仍未覆盖：浏览器级的「淘汰到 5 份」「重开浏览器后仍可恢复」，以及「替换恢复不清快照表」的独立断言。

## 3. 行为上的已知限制

- 标题上限 300 字符，超限实时提示并拒绝保存；备注与摘录同理。
- 单批导入上限 1000 条、书签文件 3 MB，超出直接拒绝，不静默截断。
- 资料选择一次最多 60 条进入提问包，超出会明确提示，不会自动截断，也不会因为「全选」就发送。
- 分类置顶最多 8 个；删除分类必须先选迁移目标，收藏一条不少。
- 「最近打开」只保留最新 15 个不同收藏。
- 工作台与弹窗共享同一份库，多标签页通过广播同步；**不同浏览器 profile 之间不同步**。
- 恢复是一道校验关：备份里任何一条缺编号、缺网址或网址不是 http / https，该条都算「无法恢复」。**替换模式会整体拒绝**（列出前几条原因，主库不动），合并模式逐条跳过并在结果里写明跳过了几条——宁可让你重导一次，也不接受「显示恢复成功、库里却少了一半」。
