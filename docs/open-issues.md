## 2. 数据风险

按「会不会丢数据」排序，前三条是必须让用户知道的。

**① 卸载扩展 = 删除全部数据。** 主库是扩展 origin 下的 IndexedDB，移除扩展时浏览器会连库一起删，没有回收站。装之前、删之前都请先导出备份。目前**没有自动备份**，也不打算在 v1a 做。

**② 换机器/换 profile，数据不跟过去。** 扩展 ID 变了，origin 就变了，库是另一个。唯一通路是导出 JSON 再恢复。新设备上库是空的，此时选「合并」等同完整导入（连设置与整理策略一起回来）；如果先手动建了分类再去恢复，就不算空库，设置会保持本机当前值。恢复时面板会提示「主库身份已切换」，旧环境还在写就会分叉——先把旧的那份停掉。

**③ 替换式恢复会清空当前主库。** 替换前会自动给当前主库拍一份完整快照，**拍快照、写副本、清库、写入是同一条事务**（`restoreWithSafety`）——快照拍完之后到提交之间没有别的标签页能插进来写，所以「刚显示保存成功的收藏被清掉、副本里也没有」这种两头空的情况不会发生；写库阶段失败则整条事务回滚，主库原样还在，也不会留下半份副本。副本同时写进本机库的 `meta`（不随替换清空），即便下载被拦、磁盘满、页面被关，回到「数据」页仍能看到「有一份替换前的安全备份还没确认保存」并重新保存；点「已确认保存」才会清掉这份临时副本。**只要这份副本还在，下一次替换会被直接挡下**（提示「还留着一份…尚未确认保存」），不会被新副本覆盖——包括「第二次替换本身失败」的情况，因为整份文件的校验排在事务之前。清理按副本编号核对，停在其他标签页的旧按钮不会误删刚存的副本。真正的风险只剩「两份都没了」时才会发生——所以替换后请确认为什么要替换，而不是把它当常规导入手段。

**④ 本地专用条目默认不进备份。** 不勾选「包含本地专用条目」，这些收藏就没了（它们本来就不该随文件走）。**同一条网址关联的待看也不会进**，三条路径都堵上了：从这条收藏「加入待看」新生成的、重新激活一条已完成待看的（会补写关联编号）、以及先独立加入待看再把同网址收藏设成本地专用的（导出时按网址再核对一次）。备份里会记下排除条数（`exclusions.readingForLocalOnly`），恢复端提示「排除过 N 条」。勾选等于把这些写进明文 JSON，自己权衡。

**⑤ 手机快照是明文。** 任何拿到 HTML 的人都能读到标题、链接、备注（如果开了备注开关）。设计上排除了本地专用与已删除条目，但**没有密码**，分享前先想清楚。

**⑥ 合并恢复不会复活本机已删的条目，也不会放宽本机的隐私范围。** 合并只新增本机没有的记录：本机已有的（包括已删除的、以及本机改过标题的）一律保留，不再按 `localRevision` 比大小——两台设备的写入次数本来就不能互相比较。判重同时看编号与网址：**同一网址、不同编号的备份收藏也绕不过本机的删除**（本机删过就跳过并计数，需要找回请到回收站单独恢复），墓碑是否生效按事务里的最终库状态判定，不会出现「在库里」又「已删除」并存。删除标记（墓碑）同样只认本机：一条收藏被设成「本地专用」再删除之后，合并一份它还是普通删除的旧备份，本机会保留 `local` 范围，不会让默认备份重新带上私密标题与网址（同网址不同编号的旧墓碑也一样；导出时还会拿墓碑的编号与网址再和本地专用条目核一遍）。代价是：**外部设备的修改不会被合并进来**，要那种效果只能用替换。恢复的是一份没有墓碑的旧备份时，界面仍会提示删除语义可能失效。

**⑦ 双设备同时写会分叉。** 没有同步机制，两台机器各写各的，只能靠备份合并。合并按 ID 与网址去重、保留本机版本，不会静默覆盖，但也**不解决「两边都改过同一条」的冲突**——它只会跳过并计数。

**⑧ AI 材料包是手动复制出去的。** 手动交接需要你自己把材料粘到外部 AI，粘出去的内容受对方隐私政策约束，扩展无法回收。材料包里已排除 `localOnly` 与 `aiBlocked` 条目，并只带白名单字段。校验通过到点「应用」之间如果改了整理策略或换了主库，应用会被拒绝：批次状态、主库身份与策略版本是在**同一条写事务里**复核的，中间没有可乘的窗口；界面会显示原因并解锁按钮，不会停在「应用中…」。

**⑨ 「彻底清空」是不可恢复的硬删除。** 为了让「清空后重新导入同一批书签」真的可行，清空会**连删除标记（墓碑）一起删**——只删记录的话，重新导入会全被判成「存在已删除收藏，未绕过墓碑」，用户看到的是「清空了却导不进来」。代价有三点：① 清空不走回收站（要能重导就不可能留软删记录），误点的第一道补救是**本机清理快照**（P9.4，保留最近 5 份，可在「数据与备份 → 最近清理」按次找回）；快照被挤掉、被手动删掉之后才真的只能靠事先导出的完整 JSON；② 墓碑没了，之后合并一份更早的备份时，这些条目会被当作「本机没有」重新带回（这正是墓碑原本要防的事）；③ 「全部收藏」页的清空会连同回收站里的记录一起清，分类页的清空只清该分类下的收藏、分类本身保留。撤销导入（按批次）不是清空：它只移除这一批新建的、之后没被改过的条目，改过的会保留并如实报数。

**⑩ 清空确认框的数量可能小于实际删除量。（2026-10-31 已修复，P9.0）** 原实现里分类页与未分类页的确认框按**当前活跃列表**计数（`items.length`），而 `purgeCategory()` 读取整张 `bookmarks` 表再按分类过滤，**连该分类下已进回收站的记录一起删**，相应的墓碑也一起清；确认框显示 120 条时实际可能删掉 130 条。

现在确认前会先查一次作用域明细（`purgeCounts` → `countPurgeAll` / `countPurgeCategory`），确认框改为「将删除 12 条记录（在库 11 · 回收站 1），并清掉 1 条删除标记」；点确认后再核对返回的实删数量，与确认时的总数不一致会明确提示而不是静默通过。证据：单测「分类清空把回收站里的记录算进来，计数与实删数量一致」「整库清空的计数包含回收站，且与实删数量一致」；`verify:p3`「清空确认框拆出在库 / 回收站 / 删除标记，且与实删数量一致」实测 `total=12 active=11 trashed=1 tombstones=1`，与主库一致。

**⑪ 撤回与清空没有清理快照。** 目前两者都是硬删，误操作只能靠**事先**导出的备份找回，本机没有留下"我刚才删了什么"的副本。批次撤回又必须硬删（要能立刻重导同一批书签），所以不能改成软删。**2026-10-31 P9.4 已落地（第一段）**：硬删前在同一事务里先写本机 `purgeSnapshots`（算候选 → 写快照 → 删除 → 记数），任一步失败整体回滚；数据页「最近清理」可预览并只找回这一次删掉的条目，冲突一律跳过不覆盖，不调用整库替换。边界：保留最近 5 份、单份 5000 条或 5 MB、总量 50 MB；**快照写不进去就一条都不删**。详见 [清理快照与单次清理恢复](purge-snapshot-and-restore-design.md)。**2026-10-31 收尾**：原先欠的三条断言已补齐——浏览器级「淘汰到 5 份」（连做 6 轮后仍为 5 条）、「重开浏览器后仍可恢复」（重启前后各 5 条、扩展 ID 不变），以及单测「替换恢复不会清掉清理快照」。

**⑫ 撤回预览的数字不保证等于实际移除数。（2026-11-02 记录：行为正确，文档与界面已同步）** 预览与执行共用同一套判据，但两次各自读一次库：确认前另一个页面改了某条、把它转成收藏或删掉，执行时会按最新状态改判为保留。这是并发保护，不是缺陷。界面已写明「这是此刻的算法结果，不是承诺：执行时会重新读一遍」，执行后若数量有差额会明确报出（例如「预览时是 3 条，实际移除 2 条：确认前有 1 条被修改…已保留」）；预览本身也改成在一个只读事务里取一致快照，不会读出拼凑的中间状态。**「处理全部匹配」不沿用这个口径**：它把候选 id 与当时的版本一起冻结，执行只认冻结清单——预览之后新增的命中不会因为「条件还成立」被卷进来，改动过的条目按版本不符跳过。代价是：极少数情况下会出现「按了 30 条、实际处理 29 条」，差额同样逐条列原因。

**⑬ 「已改动」与「回收站」在主动清理里的边界。（2026-11-02 补齐，行为已按动作区分）** 原先 `previewBatchCleanup()` 无论选哪种状态都只冻结 `untouched`，执行又无条件跳过 `deletedAt`，于是两件事做不成：① 标记已读、改过分类、应用过 AI、从清理快照恢复过的记录都会变成「已改动」，从此不能被这个入口主动清理；② 本批记录进了回收站就再也无法按本批彻底删除，「先放回收站看看、确定不要了再删并重导」只能改走整库或整分类清空（范围更大）。
现在判定收敛为一个函数 `isBatchCleanupActionable(state, destination, mode)`（`packages/core`），界面计数、预览冻结、执行复核三处共用：**移入回收站**只收列表里的记录；**彻底删除**也收已在回收站里的记录，并连墓碑一起清，因此之后能重导；**已改动**在两种动作里都可处理，但默认筛选仍是「未改动」，撤回仍强制保留已加工的条目；**待看已转收藏、已完成**不在这个入口动——删待看不牵动已转出的收藏，完成历史走自己的入口。
残留代价：彻底删除回收站里的记录同样只受「最近 5 份清理快照」保护，快照被挤掉后不可恢复；批次内清理仍只覆盖这一批，跨批次「全库按站点清」仍未做（P9.3 之后）；界面与仓库共用谓词，但两次各自读库，确认前别人又改了那条，仍会表现为「少处理 N 条」，执行后逐条报原因。

**⑭ 列表批量操作曾经绕开版本与状态保护。（2026-11-04 已修复，P9.10）** 条件清理与批次清理有冻结令牌，但列表里勾选后的移入回收站 / 恢复 / 彻底删除 / 移出待看只传编号，仓库按「当前这条是什么」就动手。复核报告复现三条：勾选的回收站记录被另一页恢复后照样被彻底删除；勾选的待看被标为完成后照样被移除；勾选后补了备注也不因版本变化跳过。界面却写着「状态在勾选后变过，按最新状态跳过」——文案与实际行为不符，等于把用户刚做的决定抹掉（硬删除还能从清理快照找回，但要用户先发现）。
现在四个入口共用一条保护边界：`prepareBulkSelection()` 在只读事务里把每条记录的 `localRevision` 与状态一起冻进 `BulkToken`，并当场报出「确认这一刻就不符合」的条数；`runBulkSelection()` 在同一读写事务里逐条复核，状态或版本变过的一律跳过并写明原因（「确认后已从回收站恢复，已保留」「确认后已完成，已保留」「确认后被修改，已保留」），不自动补最新版本绕过重新确认。确认框写明「范围冻结于 HH:mm」，执行后留一块结果卡写「已彻底删除 1 条 · 跳过 1 条：确认后被修改，已保留（标题）」。
代价与边界：冻结清单在内存里，刷新页面即失效（需重新勾选）；跳过只按「状态 + `localRevision`」判定，没有行锁，两页同时确认同一批时后一个全部跳过并报原因（不会重复删除，也不会静默合并）；硬删除快照的范围标签改成「实际删除数」，与勾选数不一致是刻意的。证据：单测「确认后被加备注的收藏不会被移入回收站」「待看勾选后被另一页标为完成，就不再被批量移出」「待看全部通过时真的删掉并留一份可找回的快照」「硬删除快照的标签只记真正删掉的条数」等 10 条；`verify:p3` 的 P9.10 四条。

## 3. 行为上的已知限制

- 标题上限 300 字符，超限实时提示并拒绝保存；备注与摘录同理。
- 单批导入上限 1000 条、书签文件 3 MB，超出直接拒绝，不静默截断。
- 收藏 / 收件箱 / 未分类 / 最近打开 / 回收站 / 分类页 / 搜索结果 / 待看 / 完成历史都按页显示，默认一页 50 条。**每页条数是全局设置**：设置页「列表显示 → 每页条数」可在 **20–50 之间自由输入**（回车或失焦生效，超出范围收敛到边界），列表底部的「每页」下拉改的是同一份设置，快捷档为 20 / 25 / 30 / 35 / 40 / 45 / 50。分页只决定「一次渲染多少行」，**处理范围与计数仍按全部命中**（彻底清空、按条件清理都不受当前页影响）。只有一页时不出分页条。
- 同一列表内**翻页会保留勾选**（翻页只是看同一份列表的另一段），提示里写明「其中 N 条在别的页」，也可以「只选本页」；换列表、换分类、改搜索、退出批量选择会清空勾选。
- 列表数据仍全量读进内存后再切片，没有游标分页或虚拟滚动：几万条量级翻页仍然流畅，但首次载入与内存占用随总量线性增长。导入批次历史是例外——它在仓库层按 `limit/offset` 真分页，不把全部批次读进内存。
- 「查看本批」「导入批次历史」与「最近清理」的快照列表及逐条明细同样按页显示（2026-11-03 起统一，不再用「再显示」往下堆）；明细可按关键词 / 类型 / 状态 / 原目录 / 站点筛，可以只勾其中几条找回，已找回的会标出来且不再计入可找回。筛选条件一变就回第 1 页，**处理范围与计数按全部命中**，不随展示截断。
- 「按条件清理」的命中计数在渲染层算：一个分类几千条时会先全读进内存再筛，没有服务端计数或虚拟滚动，展开会变慢但处理范围不受影响；「包含」选「只看回收站」时「移入回收站」天然为 0，界面按禁用处理，不会自动换成彻底删除。待看范围只含未读完的条，已完成与已转收藏仍走各自入口。
- 资料选择一次最多 60 条进入提问包，超出会明确提示，不会自动截断，也不会因为「全选」就发送。
- 分类置顶最多 8 个；删除分类必须先选迁移目标，收藏一条不少。
- 「最近打开」只保留最新 15 个不同收藏。
- 工作台与弹窗共享同一份库，多标签页通过广播同步；**不同浏览器 profile 之间不同步**。
- 恢复是一道校验关：备份里任何一条缺编号、缺网址或网址不是 http / https，该条都算「无法恢复」。**替换模式会整体拒绝**（列出前几条原因，主库不动），合并模式逐条跳过并在结果里写明跳过了几条——宁可让你重导一次，也不接受「显示恢复成功、库里却少了一半」。
