# 清理快照与单次清理恢复：设计与验收

更新日期：2026-10-31。对应 [开发进度规划](ROADMAP.md#p9--导入撤回补全与本批内清理) 的 **P9.4**，用户确认提前到 P9.1 之前实施。

本文解决两件事：**硬删除前留一份本机快照**，以及**只把这一次删掉的东西找回来**。两者必须同时交付——只存不恢复，等于把问题从「丢数据」挪成「有副本但用不上」。

## 1. 为什么恢复语义要单独设计，不能复用整库替换

`restoreWithSafety`（[open-issues](open-issues.md) ③）是**替换式恢复**：拍当前主库快照 → 清表 → 写入备份文件。它的价值在事务写法（快照与改动同一条 `rw` 事务，中途失败整体回滚），但它解决的是「换机器/换库」这个场景，语义是**覆盖**。

清理恢复的语义正好相反：

- 只能**加回**这一次删掉的条目，绝不覆盖当前数据。用户在清理后可能已经重新导入、改了标题、换了分类，那些是更新的意图。
- 不能触碰快照之外的任何记录。
- 不能清表，不能走 `restore`，不能因为恢复而让当前库少一条。

所以：**借鉴 `restoreWithSafety` 的同事务思路，恢复逻辑独立实现**。

## 2. 保护范围：哪些入口必须先存快照

代码里现有的硬删除入口共 6 条，逐项定责：

| # | 入口 | 实现 | P9.4 v1 |
| --- | --- | --- | --- |
| 1 | 全部收藏页「彻底清空…」 | `purgeAll()` | ✅ 必须存 |
| 2 | 分类页「彻底清空…」 | `purgeCategory(id)` | ✅ 必须存 |
| 3 | 未分类页「彻底清空…」 | `purgeCategory(null)` | ✅ 必须存 |
| 4 | 待看页「清空待看…」 | `purgePending()` | ✅ 必须存（只含 pending 队列，完成历史不动） |
| 5 | 完成历史页「清理完成记录…」 | `purgeCompleted()` | ✅ 必须存 |
| 6 | 导入结果页 / 数据页「撤销这次导入」 | `undoBatch(batchId)` | ✅ 必须存（两处入口同一个用例） |

不存快照的入口（明确排除，避免做成一刀切）：

- **移到回收站**（`softDelete`）、**移除单条待看**：可恢复/可重加，不属于硬删。
- **整库替换恢复**：已有独立的安全副本机制，不并入本表；但它**不得清掉 `purgeSnapshots`**（见 §5）。
- **删除分类**：不删收藏，只迁移引用，不属于硬删。

待看类清空必须在确认文案里写明「待看没有回收站，清掉只能从清理快照找回」，不能与「收藏可恢复」混为一谈。

## 3. 快照怎么写

同一 `rw` 事务内完成四步，任一步失败整体回滚（沿用 `restoreWithSafety` 的写法）：

```
算候选 → 写 purgeSnapshots → 删除 → 更新快照计数字段
```

表结构（Dexie `version(3)` 新增对象仓库，索引 `createdAt`）：

```ts
interface PurgeSnapshot {
  id: string;
  createdAt: string;
  /** 触发入口：all / category / uncategorized / readingPending / readingCompleted / importBatch */
  entry: string;
  /** 作用范围的可读描述，用于界面显示，例如「分类：开发」「批次：bookmarks.html」 */
  scopeLabel: string;
  /** 删除前的主库身份指纹，用于提示「这是另一台机器的快照」 */
  dbFingerprint: string;
  /** 实际删掉的条目，按类型分组；恢复只认这里 */
  bookmarks: Bookmark[];
  readingItems: ReadingItem[];
  tombstones: Tombstone[];
  /** 统计，便于列表展示与恢复后核对 */
  counts: { bookmarks: number; readingItems: number; tombstones: number };
  /** 恢复结果；null 表示尚未恢复 */
  restoredAt: string | null;
  restoredCounts: { restored: number; skipped: number; conflicted: number } | null;
}
```

约束：

- 快照内容与备份 JSON 同级敏感（含标题、网址、备注），**只存本机 IndexedDB**，不上传、不随备份导出、不写日志。
- 不含凭据或 AI 配置；不含策略与设置（它们不参与清理）。
- 快照写入条数与候选条数必须一致，不一致视为写入失败并回滚。

## 4. 恢复语义：只找回这一次删的

界面入口：「数据与备份 → 最近清理」，列出快照（时间、入口、范围、条数、是否已恢复），可预览后再恢复。

恢复预览（必须，不直接执行）：

```
这一次清理删了 128 条收藏、12 条待看、128 条删除标记。
可找回 121 条；已存在同网址 5 条（将跳过）；分类已删除 2 条（将落到未分类）。
```

冲突处理矩阵——**默认一律不覆盖当前数据**：

| 情况 | 判定 | 处理 |
| --- | --- | --- |
| 同 `id` 已存在且 `lifeState = active` | 已经是当前数据 | 跳过，计入 `skipped` |
| 同 `id` 已存在但在回收站 | 用户后来删过它 | 跳过，保持回收站状态，提示「需要请到回收站恢复」 |
| 同 `id` 不存在，但 `canonicalUrl` 已存在 | 清理后重新导入过 | 跳过，计入 `conflicted`；**不覆盖不合并**，列出被跳过的标题供人工判断 |
| 同 `id` 不存在，`canonicalUrl` 命中墓碑 | 这个网址曾被删过 | 删除该墓碑后重建记录（与导入绕过墓碑的规则一致） |
| 原分类已被删除 | 找不到引用 | 落到未分类，计数提示 |
| 待看记录恢复时同 `id` 已存在 | 用户后来重新加过 | 跳过；若已 `completed` 则不回退状态 |

其它规则：

- 恢复写入的记录按**新记录**处理：`revision = 1`、`localRevision = 1`、`lifeState = active`，不复活墓碑（除上表第 4 行）。
- 恢复完成写 `restoredAt` 与 `restoredCounts`，同一快照可重复恢复（幂等：第二次全部命中「已存在」而跳过），不删除快照本体。
- 恢复**不调用** `restore` / `restoreWithSafety`，不 `clear` 任何表，不触碰快照之外的记录；执行前在事务内复核候选，预览后被改动的条目按上表重新判定而**不静默纳入**。
- 待看恢复只影响 `readingItems`；批次撤销的恢复只重建被撤销的收藏，不重开批次状态（批次保持 `reverted`，避免与「同一批只能撤销一次」冲突）。

## 5. 容量与失败规则

| 规则 | 取值 | 行为 |
| --- | --- | --- |
| 保留份数 | **最近 5 份** | 第 6 次清理时淘汰最旧一份；淘汰只针对已恢复或最旧的，界面标注「更早的快照已自动清理」 |
| 单份上限 | **5000 条或 5 MB**（先到者为准） | 超限时**拒绝清理**，提示先导出完整 JSON 再清 |
| 总量上限 | **50 MB** | 超限时提示先清理旧快照，不自动删除未恢复的快照 |
| 空间不足 / 配额超限 | 写快照失败 | **立即中止，一条都不删**；提示「空间不足，未删除任何数据」 |
| 删除阶段失败 | 事务内异常 | 整体回滚：记录与快照都回到清理前，不留「删了一半」的状态 |
| `navigator.storage.estimate()` 不可用 | 无法预判 | 跳过预检，按写入异常处理（同上，失败即中止） |

不得为了「先删了再说」而把快照写成异步、非事务的后台任务——那会重新制造 open-issues ⑨ 的两头空风险。

## 6. 验收条件

功能完成的标准是下面全部满足，缺一条视为未完成：

**A. 保护范围（§2）**
1. 六个入口各做一次清理，都能在「最近清理」里看到对应快照，条数与实删一致。
2. 移到回收站、移除单条待看不产生快照。

**B. 恢复（§4）**
3. 恢复只加回该快照条目，当前库其它记录逐字段不变（对比前后指纹）。
4. 同网址已重新导入 → 恢复跳过并计数，当前记录不被覆盖。
5. 原分类已删 → 恢复到未分类并提示。
6. 复用替换恢复入口不会清掉 `purgeSnapshots`。

**C. 容量与失败（§5）**
7. 快照写入失败（模拟配额超限）→ 删除未发生，主库条数不变。
8. 删除中途失败（注入异常）→ 整体回滚，快照不残留。
9. 第 6 次清理淘汰最旧快照，保留数量恒为 5。
10. 超过单份上限时拒绝清理并给出明确文案。

**D. 生命周期**
11. 清理后关闭并重开浏览器，快照仍在且可恢复。
12. 预览后、执行前改动数据 → 恢复按最新状态重新判定，不静默纳入。

**测试落点**：单测覆盖 7/8/10/12 与冲突矩阵全部 6 行；`verify:p3` 覆盖 1/3/9/11（真实浏览器、真实 IndexedDB）；手册补一条 3 分钟用例（清理→重开→恢复）。

## 7. 未定项

- 快照是否提供「下载为 JSON」：默认不做（备份已有完整导出），等真实需求再补。
- 恢复是否要按条目勾选：v1 整份恢复 + 跳过清单，不做逐条勾选。
- 淘汰策略在「未恢复的快照」上是否要二次确认：v1 直接淘汰并提示，不做拦截。
