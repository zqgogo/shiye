## [P2] 列表批量操作绕开了确认版本与状态保护

位置：

- `apps/workspace/src/pages.tsx:352–361`：列表选择保存的是 ID，执行仅传 ID 数组。
- `packages/storage/src/repositories.ts:370–378`：批量移入回收站只检查当前是否存在、是否已删除，不比较确认版本。
- 同文件 `442–450`：收藏批量硬删按 ID 获取当前记录，正常/回收站均可删，不核对用户确认时的状态。
- 同文件 `975–983`：待看批量硬删按 ID 取记录，不核对是否仍 pending、是否已经转收藏/完成，以及版本是否改变。

### 独立复现

1. 收藏先进入回收站，页面 A 持有勾选 ID；页面 B 恢复收藏；A 调用批量硬删，仍删除恢复后的正常收藏，返回删除 1 条。
2. 待看被页面 A 勾选，页面 B 将其标为完成；A 批量移除，仍删除这条完成历史记录，返回删除 1 条。
3. 收藏被勾选后，页面 B 新增备注；A 批量移入回收站，没有版本冲突，修改后的记录仍被移入回收站。

前两条会将用户刚做出的恢复/完成决定一并抹掉。硬删除仍有清理快照，因此不是完全没有后路；但用户必须发现并手动找回。页面 effect 会尽量剔除不再属于当前列表的 ID，无法代替数据库事务内的校验：跨页的修改和状态变化仍可能发生在最后一次 UI 刷新之后、实际写入之前。备注改动也不会使记录离开列表，因而不会触发这种剔除。

同轮新增的条件清理已有冻结令牌和版本复核，独立对照验证能正确保留确认后变化的记录；缺口来自两种批量入口没有共用这条保护边界。现有页面结果文案声称“状态在勾选后变过，按最新状态跳过”，但只传 ID 无法兑现这项保证。

### 修复建议

- 列表批量确认生成包含实体类型、ID、当前版本、生命周期/待看状态及动作的候选清单。已明确选中的“之前就改过”的条目仍可处理；保护的是确认之后的新变化。
- 仓库事务内核对版本及状态，再软删/恢复/硬删；变化的条目逐项跳过并报原因。不要通过自动补上最新版本绕过用户重新确认。
- 待看批量移除至少应拒绝已完成/已转收藏的条目；回收站发起的硬删至少应拒绝确认后已恢复的正常条目。正常收藏列表发起的明确硬删仍可保留，不能用全局“只能删回收站”替代动作范围校验。
- 复用已存在的条件清理冻结/事务检查原则，硬删除继续保持快照写入与删除同事务。
- 正式测试补齐：确认后编辑、确认后恢复、确认后完成/转换、跨页勾选期间变化，以及快照失败不删。
