# 拾页独立检查报告

检查日期：2026-10-29。依据仓库当前代码、v2.1 产品与技术说明、原始验收清单，以及引用对话中可读取的需求。检查前 Git 工作区干净。本次没有修改产品代码。

## 结论

主要功能已落地，但还不宜按「数据安全与需求验收全部完成」收口。发现的重点集中在备份恢复、隐私在关联数据之间的边界，以及 AI 校验与真正应用之间的时序。

下面 8 个场景已通过独立用例复现当前问题（编号 1、2、3、5、6、7、8、9）；另有 2 项通过代码确认（编号 4、10）。「复现通过」表示成功观察到缺陷，不代表功能符合预期。

## 优先修复

### 1. [P1] 合并恢复可能覆盖本机删除，墓碑没有参与恢复判定

位置：`packages/storage/src/backup.ts:363`，特别是 365–382、398–400 行。

复现：创建收藏并导出 → 本机删除 → 合并另一设备上同 ID、较高 localRevision 的活跃副本。结果收藏重新变成 active，同时同 ID 的删除墓碑仍在。

原因：写收藏时只比较 localRevision；墓碑在后面单独 put，既没有阻止复活，也没有与实体状态协调。两个设备的本地修订号只能表示各自写入次数，不能单凭数值判断哪一边修改应该胜出。类似流程也可能覆盖本机人工修改。

建议：明确同 ID 冲突策略，默认保留本机或列出冲突供用户处理；在同一事务内裁决实体与墓碑。补「本机已删除 + 外部活跃高修订」「本机人工修改 + 外部高修订」回归。现有文档中“合并不会静默覆盖”“墓碑阻止复活”的表述需要随实现修正。

### 2. [P1] 结构合法、条目字段损坏的备份可清空主库并显示恢复成功

位置：`packages/core/src/schemas.ts` 的 `BackupEnvelopeSchema`，`packages/storage/src/backup.ts:247`。

复现：合法备份信封的 bookmarks 改成 `[{"title":"缺少 ID 和 URL"}]` → 选择替换恢复。预览按原始数组显示 1 条；恢复清洗阶段返回 null 并过滤，最后新增 0 条、当前收藏清空，没有任何“记录损坏被丢弃”告警。

建议：在破坏性操作前完成逐条校验；遇到无法恢复的行阻止替换，展示行号与原因。若提供“跳过损坏记录”模式，必须明确展示真实可恢复数量并单独确认，不能把有效 JSON 等同于有效备份。

### 3. [P1] JSON 恢复可以绕过 http/https 链接限制

位置：`packages/storage/src/backup.ts:42`、`:119`。

复现：把备份中 originalUrl 改为 `javascript:alert(1)`，保留原有合法 canonicalUrl → 替换恢复成功，主库 originalUrl 仍为 javascript 链接。

原因：originalUrl 校验抛错后，只要输入自带 canonicalUrl 就继续接受；canonicalUrl 本身也未重新校验。UI 多处直接把 originalUrl 放入 href / window.open。

建议：恢复时与普通创建共用 URL 白名单，canonicalUrl 必须由已校验的原始链接重新生成；不可信的派生字段不能充当校验兜底。打开链接前也做防御性检查。本次证实的是非法链接进入主库，未声称成功执行脚本或绕过扩展 CSP。

### 4. [P1] 替换前的安全备份实际只生成在内存，下载在替换完成之后才发起

位置：`packages/application/src/workspace.ts:404`；`apps/workspace/src/data.tsx:93`、`:117`。

调用顺序：导出 JSON 到内存 → 替换事务提交 → 返回 UI → 发起安全备份下载。代码确认，未注入浏览器崩溃进行验证。

影响：替换已经提交、下载尚未发起或保存失败时，关闭页面会丢掉唯一的内存副本；事务回滚只能处理事务内失败，无法撤销已经提交的替换。因此界面的“替换前先自动导出”承诺不成立。

建议：先把安全副本持久化到不会被替换清除的独立位置，或完成可确认的文件保存步骤，再开始替换；失败时保留旧库。测试应验证操作顺序与下载失败分支，不能只检查最终下载目录里有文件。

### 5. [P1] 本地专用收藏可经关联待看泄露到默认备份

位置：`packages/storage/src/backup.ts:226`；`apps/workspace/src/components.tsx:205`。

复现：创建 localOnly 收藏 → 使用“加入待看”（会复制标题、URL 并记录 relatedBookmarkId）→ 不勾选“包含本地专用条目”导出。bookmarks 中没有这条收藏，但 readingItems 原样包含其标题与网址。

这是关联数据的隐私边界缺口；不会自动发送到外部，但用户携带默认备份时仍会带走这些内容。

建议：明确待看的隐私模型。至少在导出时识别关联本地专用收藏的待看，过滤或要求明确确认；还需覆盖“加入待看后才把收藏设为本地专用”的情况。

### 6. [P2] AI 回复通过校验后，策略变化不能阻止旧建议被应用

位置：`packages/application/src/workspace.ts:430`；`packages/storage/src/repositories.ts:352`。

复现：生成整理包 → 校验合法回复 → 另一个标签页修改整理策略 → 在原预览应用。应用成功，旧策略输出写入收藏。

原因：policyVersion 只在 validateAiReply 检查。applySuggestions 和每条应用事务没有重新检查当前策略、批次状态及主库身份。现有版本与隐私检查无法代替策略检查。

建议：应用事务同时读取批次、当前主库身份和 policyVersion，再决定是否写入；补“预览通过后策略变化”的时序回归。当前 P5 中“策略变化后重新校验被拒绝”覆盖不了这个窗口。

### 7. [P2] 完整备份往返会丢失来源目录与来源记录

位置：`packages/storage/src/backup.ts:94`、`:142`。

复现：创建带 sourceFolder、importBatchId 的书签和待看 → 导出 → 替换恢复。收藏来源只剩 sourceType/capturedAt，originalFolder/importBatchId 被丢弃；待看 sources 直接变成空数组。

建议：按 SourceInfo 白名单逐字段恢复，保留来源目录。若恢复不携带 importBatches，明确 importBatchId 的处理语义，避免制造不可访问的历史入口。补字段级往返测试，不能只比收藏条数。

### 8. [P2] 合并恢复待看仅按 ID 判重，破坏同网址唯一性

位置：`packages/storage/src/backup.ts:386`。

复现：本机与备份中各有一条同 canonicalUrl、不同 ID 的 pending 待看 → 合并 → 列表出现两条。普通 add 路径会拒绝此重复，恢复路径却没有检查。

建议：按 canonicalUrl 合并待看并明确 pending/completed 的冲突策略，处理 relatedBookmarkId 引用；同样检查替换文件自身的重复项。

## 还需收口的体验与需求

### 9. [P2] 新设备空库使用默认“合并”不会恢复策略与置顶设置

位置：`packages/storage/src/backup.ts:409`、`:428`；`apps/workspace/src/data.tsx` 的恢复方式文案。

复现：导出自定义策略与置顶分类 → 在全新数据库打开工作台（自动创建默认设置）→ 用默认合并恢复。收藏和分类导入，但策略仍是默认策略，置顶分类为空。

保留现有设置可以是合并的合理设计，但当前“当前主库为空，等同于导入”的说明容易让换机用户以为完整恢复。建议提供“首次迁移完整恢复”，或在预览中明确列出合并不会恢复的设置、策略和主库身份。

### 10. [P2] 读取划词仍静默截断，而且用 UTF-16 长度截断

位置：`apps/extension/src/popup/Popup.tsx:66`；`apps/extension/src/background/service-worker.ts` 的 saveFromMenu。

代码确认：划词读取执行 `.slice(0, 4000)`，右键保存也截断选中文字；没有提示用户丢掉了后半段。与规格“4,000 Unicode 码点、超出明确提示、不静默截断”不一致。emoji 等字符还会更早达到 UTF-16 长度，并可能切断代理对。

建议：先获得完整选中文字，按码点检查；超限让用户缩短或显式确认裁剪。标题截断也应按同一套字符语义处理。

### 顺带修掉的验证脚本缺陷

`verify:p6` 里「同一天连续导出得到两个不同文件」这一条，脚本连点两次会落在**同一秒**（文件名精确到秒），自己造出同名覆盖。两次导出之间加了 1.2 秒间隔，把节奏还原成人工操作；断言语义不变。
