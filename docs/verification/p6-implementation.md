# P6 备份、恢复与手机快照：补齐一致性与设备验证

更新日期：2026-10-29。对应 [P6 任务](../ROADMAP.md#p6--备份恢复与手机快照)。

## 1. 原有实现与本轮补齐

P6 的三条主路径此前已通：完整 JSON 导出、合并/替换恢复、手机只读 HTML 快照，界面上也有对应面板。对照任务书逐条核对后，补的是「恢复之后数据还站得住」的部分：

| 缺口 | 原来的问题 | 现在的行为 |
| --- | --- | --- |
| 恢复后可能留下悬空引用 | 备份引用的分类或标签不在本次恢复范围内时，`categoryId` / `tagIds` 原样写库，之后分类页、未分类计数与搜索都对不上 | 恢复前收集本次真正写入的分类/标签 ID，清空指向它们的引用，`danglingReferences` 逐处计数并写入警告 |
| 替换不重置策略 | 备份里 `policy` 为空时，本机旧策略原样留着；「替换成备份那一刻」并不成立 | 替换模式固定写策略：有则用备份的，没有则写默认策略并说明 |
| 主库身份两处来源不一致 | 恢复只采信 `settings.libraryId`；跨设备备份真正的身份在信封顶层 `libraryId`，两者不一致时切换检测失效 | 身份以信封顶层为准，替换时比较前后值，返回 `librarySwitch` 供界面提示 |
| 旧 AI 映射不失效 | 替换会清 `handoffBatches`，但结果里看不出来，用户不知道旧批次已经作废 | 记录 `handoffInvalidated` 数量并写入警告；界面提示「旧设备或旧配置上的 AI 交接映射已失效，请停止旧库写入」 |
| 安全备份的时间与数量看不到 | 替换前确实导出了安全备份，但只在界面上给了一个「再次保存」按钮 | 结果区展示安全备份的导出时间、收藏/待看/分类/标签条数，并说明文件已发起下载 |
| 恢复失败提示不显示（真实缺陷） | 文件选好之后，`doRestore` 写的错误只落在 state 里；「替换未勾选确认」这类拒绝用户完全看不到 | 文件已解析时也在操作按钮下方渲染失败原因 |
| 备份里的策略可能是 null | 从未打开过策略页时库里没有 `default` 行，导出写成 `policy: null`，恢复后说不清当时用哪一版 | 导出「此刻生效的策略」：缺省时写入默认策略对象 |
| 损坏 JSON 的提示是 V8 原文 | 直接抛 `Unexpected end of JSON input` | 统一说「文件不是有效的 JSON，请确认选对了备份文件」 |

单测由 58 项增至 **68 项**（本轮 +7）：悬空引用清空与计数、替换重置默认策略、主库身份切换与批次作废、替换中途失败整体回退、合并跳过较旧记录、空主库合并等同导入、快照组合筛选属性且不加载外部资源；另有 3 项导出文件名单测（同日两次不重名、快照文件名带时分秒、非法时间仍可用）。

## 2. 关键设计取舍

**为什么主库身份取信封顶层。** `settings` 是随备份一起走的普通对象，可能被手改、也可能来自旧格式；顶层 `libraryId` 是导出那一刻写死的设备主库标识。恢复后要回答的是「现在这份库还是不是原来那份」，只能认顶层。两者不一致时以顶层为准，并如实提示切换。

**为什么清空悬空引用而不是自动建分类。** 备份里没有的分类，名字也无从得知（只能拿到一个 ID）。凭空建一个「未知分类」会把用户的分类体系搅乱；清空并计数，至少让「未分类」是真实可操作的入口，用户能自己重新归类。

**为什么安全备份写成文件而不是写库。** 替换会把主库清空，写进同一个库的备份也会一起没。安全备份必须离开这个库，所以走浏览器下载；界面负责把时间与条数说清楚，并留一个「再次保存」的入口。

**为什么替换要作废 AI 批次。** 在途批次的编号映射指向旧库的条目 ID。留着它，刷新后「继续这一批」会把建议应用到新库里同 ID 的另一条记录上——这比丢掉一批更糟。

## 3. 页面级回归：`npm run verify:p6`

回归不读内存字符串，而是用 CDP 的 `Browser.setDownloadBehavior` 把浏览器下载目录指向 `.verify/downloads-p6`，再读磁盘上用户真正拿到的那份 JSON / HTML。

### 造数方式

先用界面建 1 条真实收藏当字段模板，再用原生 IndexedDB 复制变体，并补上分类、标签、待看、墓碑与一个在途 AI 批次：

- `P6 模板收藏`：普通条目；
- `P6 普通收藏`：挂分类与标签，带人工备注与选中文字（验证快照两个开关）；
- `P6 本地专用`：默认不进备份、不进快照；
- `P6 禁止AI`：`aiBlocked` 不等于禁止普通导出，应当留在备份与快照里；
- `P6 已删除`：不进快照，但连同墓碑进备份。

### 首轮失败与修复：导出文件名只到「日」

首轮在普通终端执行时 30 项里 6 项失败：`P6.1 导出完整 JSON` 与 `P6.3 导出手机只读快照` 两处「等待下载超时」，以及 P6.2 的三个阶段（`Cannot read properties of null`——前置的 `localOnlyBackup` 没拿到，连带崩掉）。

根因不是下载被拦，而是**同名覆盖**。脚本里的点击不是用户手势，第二轮起走的是无交互下载路径，文件名相同时 Chrome 直接覆盖而不是加 ` (1)`：第一份 6122 字节、第二份 7074 字节，磁盘上却只有一个 `shiye-backup-20261029.json`。`waitForDownload` 只认「已知文件之外的新文件」，于是永远等不到。这是真实缺陷，不是脚本问题——`backupFileName` / `snapshotFileName` 都只截到日期：

| 原来 | 现在 |
| --- | --- |
| `shiye-backup-20261029.json`（同一天导出第二次就重名） | `shiye-backup-20261029-123752.json`（本地时间到秒） |
| `shiye-collection-20261029.html` | `shiye-collection-20261029-123752.html` |

对用户的实际影响：一天里导出两次（比如先备份、替换前又自动存一份安全备份）文件名一模一样，Chrome 会存成 `… (1).json`，事后分不清哪份是替换前的安全备份；走无交互下载时更直接，前一份被覆盖。文件名精确到秒之后，安全备份与当次导出一目了然。

配套改动：

- `packages/core/src/time.ts` 新增 `fileStamp()`（本地时间 `YYYYMMDD-HHmmss`，无法解析时退回当前时间），`backup.ts` 两个文件名函数改用它；
- 新增 `packages/core/src/backup.test.ts` 3 项：同日两次导出不重名、快照文件名带时分秒、非法时间仍给出可用文件名；
- `verify:p6` 增加一条断言「同一天连续导出得到两个不同文件，前一份没有被覆盖」，把这次缺陷钉住；
- `waitForDownload` 超时时带上「目录内已有几个、几个未完成、CDP 下载事件流水（开始/完成/被取消）」，下次能直接区分「没触发下载」和「下载了但没落在这里」；
- P6.2 三个阶段加前置校验，缺 `localOnlyBackup` 时明确写「缺少前置数据」，不再抛 `TypeError`。

## 4. 未验证项

1. **P6.4 手机真机**：自动化只能确认 HTML 结构、体积与移动端可读性所需的静态资源，无法代替真机。需要把 `.verify/artifacts/p6-snapshot-mobile.html` 传到手机浏览器打开，记录设备、浏览器、分类与关键词组合筛选的实际表现。
2. **系统级下载失败**：只验证到 Chrome 下载目录里出现完整文件；磁盘已满、用户取消保存、下载目录无权限等情况未覆盖。
3. **跨浏览器配置迁移**：替换后提示「旧库停止写入」是文案与数据层的作废，真实双设备同时使用的分叉风险无法在本环境复现。

## 6. 独立检查后的加固（2026-10-29）

独立检查（[报告](independent-review-2026-10-29.md)）在恢复链路上找出 5 处会丢数据或漏数据的缺陷，P6 范围内的加固如下：

| 缺陷 | 修法 | 断言 |
| --- | --- | --- |
| 合并恢复按 `localRevision` 比大小，会用另一设备的备份复活本机已删条目，并留下冲突墓碑 | 合并改为只新增：本机已有的一律保留并计数；写删除态补墓碑、写活跃态清同 ID 墓碑；备份里与活跃记录冲突的墓碑被忽略并计数 | 单测「合并不会复活本机已删除的收藏」「合并不覆盖本机同 ID 的人工修改」 |
| 条目字段损坏的备份在替换时被静默过滤，结果显示恢复成功、主库已空 | 清洗逐条收集拒绝原因；替换模式有任意一条不可恢复就整体拒绝（`INVALID_BACKUP_RECORDS`），主库不动；合并模式跳过并写明条数 | 「结构合法但条目损坏的备份在替换时被拒绝，主库不动」 |
| 恢复采信备份自带的 `canonicalUrl`，`javascript:` 链接可借合法派生字段进库 | 一律由 `originalUrl` 重新规范化；另在四处外链渲染/打开前加 `isHttpUrl` 纵深防御 | 「伪造 canonicalUrl 不能把 javascript: 链接带进主库」 |
| 替换前的安全备份只在内存，下载在替换提交之后才发起 | 先写 `meta.safetyBackup`（不参与替换清空），再提交替换；数据页检测该副本并提供重新保存，确认后才清理 | 「替换前的安全备份在提交前就落库，替换失败也能取回」 |
| 本地专用收藏「加入待看」后，衍生待看照常进默认备份 | 导出按 `relatedBookmarkId` 过滤，并记 `exclusions.readingForLocalOnly`；恢复端提示排除了几条 | 「本地专用收藏关联的待看不进默认备份，但会说明排除了几条」 |

另外修了两处脚本自身的问题：连续导出会落在同一秒（已加 1.2 秒间隔）、`verify:p6` 的 32 项里新增了合并语义的数据断言。

加固后复跑：`verify:p6` **32 项全通过**，`npm test` 79 项通过。

## 7. 第二轮复核后的加固（2026-10-30）

第二轮复核（[报告](independent-recheck-2026-10-30.md)）指出：上一轮把安全备份「落库」当成已交付，但固定键 `put` 会被下一次替换覆盖，而且覆盖发生在逐条校验之前——第二次替换即使失败，第一份（原始数据）也已经被顶掉。同一轮还发现合并裁决只按 ID 查墓碑。

| 缺陷 | 修法 | 断言 |
| --- | --- | --- |
| 未确认的安全备份被下一次替换覆盖，失败的那次也会覆盖 | 副本带 `id`；`saveSafetyCopy` 遇到已有副本直接抛 `SAFETY_COPY_PENDING`，替换被挡下、主库不动；清理按 `id` 核对，旧标签页不会误删新副本 | 「第二次替换失败不会覆盖尚未确认的安全备份」「未确认的安全备份存在时下一次替换被挡下，清理按编号核对」 |
| 逐条校验发生在保存安全副本之后 | 抽出 `prepareRestore()`，`validateRestore()` 与 `restore()` 共用同一套清洗判定；服务层先校验再保存副本 | 「伪造 canonicalUrl…」「结构合法但条目损坏…」两条替换类用例仍然拒绝，且不再触碰安全副本 |
| 同网址、不同 ID 的备份收藏绕过本机删除 | 合并时按 `canonicalUrl` 同时查活跃、已删除与墓碑（含仅在网址上命中的），命中即跳过并计 `keptLocalDeletes` | 「合并时同网址、不同编号的备份收藏不能绕过本机删除」 |
| 墓碑冲突按备份数组判定，会给本机活跃收藏写墓碑 | 改为在事务里查该 ID 的最终实体，活跃则忽略这条墓碑 | 「合并只含墓碑的备份不会给本机活跃收藏写墓碑」 |
