## 1. [P1] 合并旧删除标记会降低本机隐私范围，默认备份再次暴露私密标题与网址

位置：[packages/storage/src/backup.ts:678](../../packages/storage/src/backup.ts#L678)，关联导出过滤在同文件 434–436 行。

复现完全使用正常用例，不需要伪造备份字段：

1. 创建普通收藏，删除，导出一份旧备份；删除标记 `privacyScope` 为 `main`。
2. 本机恢复该收藏，改为“本地专用”，再删除；此时本机删除标记正确为 `local`。
3. 默认导出不包含该收藏的标题与网址，符合预期。
4. 合并第 1 步的旧备份。
5. 收藏实体因为同 ID 已存在被保留，仍然是本地专用；但删除标记被后面的无条件 `put` 覆盖，`privacyScope` 从 `local` 变回 `main`。
6. 再次默认导出时，收藏数组中没有它，删除标记数组却包含标题和 canonicalUrl。

影响：用户没有勾选“包含本地专用条目”，文件仍携带私密元数据。新加的待看过滤无法覆盖这条路径。

建议：

- 合并墓碑时同样保留本机已有状态，不能只对收藏实体执行“只新增”。
- 当前实体或本机已有墓碑表明它属于本地专用时，不接受外部旧记录将隐私范围降级。
- 导出删除标记时再与本机实体的隐私做交叉核对，避免只信 `privacyScope`。
- 补充“普通删除 → 导出 → 恢复并改私密 → 再删除 → 合并旧备份 → 默认导出”的完整回归。

证据：`.verify/review-2026-10-30-round3/boundaries.test.ts` 第一条。已确认主记录 `privacy.localOnly=true`，删除标记却为 `main`，默认 JSON 含标题与网址。

## 2. [P1] 安全快照与替换提交分属不同事务，并发成功写入可同时从主库和副本消失

位置：[packages/application/src/workspace.ts:411](../../packages/application/src/workspace.ts#L411)，特别是 412、415、417 行。

当前操作顺序为：

```text
只读事务导出当前库
→ meta 事务保存安全副本
→ 全库写事务执行替换
```

安全副本现在可以防止重复覆盖，但这三个步骤之间仍允许其他标签页或扩展弹窗写入。

复现：

1. 开始一次替换恢复，导出并持久化安全副本。
2. 在替换事务开始前，用同名数据库的第二个连接新增一条收藏，等待事务提交，确认新增成功。
3. 继续执行替换。
4. 新收藏被替换清掉；安全副本是在它出现之前生成的，也没有这条收藏。

本轮用独立第二个 Dexie 连接提交真实写入，只在 `saveSafetyCopy` 返回前插入可控调度点，没有伪造收藏写入成功。它代表另一个标签页/扩展弹窗与恢复流程正常交错的情况。

影响：刚显示保存成功的内容可能无法从任何安全副本找回。事务内回滚不能保护事务开始前这段窗口。

建议：把“读取替换前主库 → 写入安全副本 → 清库与恢复”放进同一个覆盖相关表的仓储写事务。备份文件下载可以在提交之后发起；输入校验可以提前做。若采用全局恢复锁，该锁必须由所有写入入口在事务内检查，单纯禁用当前数据页按钮不能阻止其他页面写入。

测试应验证：第二连接的写入要么被纳入安全副本，要么在替换后正常保留，要么明确失败；不能先成功、随后主库和副本都找不到。

证据：`.verify/review-2026-10-30-round3/boundaries.test.ts` 第二条。

### 行为变化

- 替换在写库阶段失败时：以前主库已被清空、只剩 `meta` 里的安全副本；现在整条事务回滚，主库原样还在，也不再留下半份副本。旧单测「替换前的安全备份在提交前就落库，替换失败也能取回」因此改写为「替换写库失败时主库原样还在，也不留下半份安全副本」，并在同一用例里补验「成功替换仍会在提交前落库」。
- 合并时墓碑冲突会多两句提示：「N 条删除记录在本机已有更新的状态」「N 条删除记录的隐私范围按本机的本地专用保留」。
