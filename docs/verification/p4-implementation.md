# P4 分类、搜索与提问资料选择：缺口补齐与回归覆盖

更新日期：2026-10-28。对应 [P4 任务](../ROADMAP.md#p4--分类搜索与提问资料选择)。

## 1. 本轮补齐的实现缺口

P4 的界面（分类管理弹窗、资料选择器、搜索页）此前已存在，但对照任务书有五处只做了一半。本轮按条目补齐：

| 缺口 | 原来的问题 | 现在的行为 |
| --- | --- | --- |
| 置顶分类上限只在界面校验 | `setPinnedCategories` 直接写库，绕过界面调用 API 可置顶任意多个 | 用例层去重、丢弃未知 ID、超过 `LIMITS.pinnedCategories`（8）时抛 `INVALID_INPUT` |
| 搜索每次全量重建索引 | `search()` 每次都 `listActive()` 后重建 MiniSearch，500 条下每次输入都要重新分词整库 | 按数据指纹缓存索引（id + localRevision + 分类 + 标签 + 分类名 + 标签名），只在数据变化时重建 |
| 没有显式的索引入口 | P4.2 要求「索引重建」，但界面上无处触发，索引坏了只能刷新页面 | 用例层新增 `rebuildSearchIndex()`，搜索页加「重建索引」按钮并提示文档数 |
| 搜索只有全库 | P4.5 要求「支持全库 / 当前分类」 | 搜索页新增「检索范围」下拉，用例层 `search(query, { categoryId })` 在命中集上按分类过滤 |
| 待看没有独立搜索 | P4.5 要求「待看独立搜索」，待看页只能按加入时间看全量 | 待看页新增搜索框，只查队列本身（标题 / 网址 / 备注），显示「匹配 N / 共 M 条」 |
| 选择集可能残留不合格项 | 资料选择时若某条被设成本地专用或删除，`selected` 仍留着它的 ID，「已选 N 条」比实际能用的多 | `AskPage` 在数据变化时用 `useEffect` 剔除不合格 ID；`buildAskPack` 本来就有隐私兜底，现在界面计数也一致了 |
| 分类改名后索引靠重建才更新 | 改名不会主动失效索引（虽然指纹机制能兜住） | `renameCategory` 改名后显式重建一次，语义明确 |

配套的单测从 42 项增到 48 项：检索范围、改名后旧名失效、回收站排除与重建计数、置顶上限与去重、删除分类只迁移引用，以及八个字段各自命中且互不串味。

## 3. 未验证项

三项写进报告 `limitations`：

1. **「即时排除」的即时性**：选择集随数据变化自动收缩的逻辑由 `useEffect` 完成，页面级只能验证「不合格条目不出现在列表里」；收缩本身由用例层单测覆盖（`buildAskPack` 排除隐私项）。
2. **搜索索引故障**：Dexie 不提供故障注入，界面上无法原生触发索引损坏。本轮验证的是「重建索引」按钮、无匹配与空库状态。
3. **跨会话保留选择状态**：路由切换会卸载页面组件，已选资料随之丢失，这是 v1a 的既定取舍（不引入跨会话草稿）。本轮只在同一页面会话内验证筛选与选择状态。

## 5. 三轮回归的失败定位与修复

### 第一轮：15 项失败，两个根因

失败表面上分散在搜索、分类、待看三处。

**根因 A：搜索页不写地址栏，路由与 hash 脱钩（产品缺陷）**

现象：`P4.1 置顶上限与排序`、`P4.1 删除分类不删收藏`、`P4.5 中文召回与待看独立搜索` 三项都以「等待文本超时：管理分类 / 快速操作」中断，而页面停在上一页。

`setQuery` 里只有 `setRoute('search')`，没有改 `location.hash`；`navigate()` 用的又是 `history.replaceState`，不会触发 `hashchange`。于是出现「内部路由是 search、hash 还停在上一页」的错位，此后任何 `window.location.hash = 'rules'` 都成了空操作（目标值与现值相同，浏览器不发事件），页面就卡在搜索页。

这不只是脚手架问题：搜索时地址栏指向错误的位置，复制该地址重新打开会进错页，前进/后退读回的也是错的一页。

修复（`state.tsx`）：`setQuery` 进入搜索时同步 `replaceState('#search')`。第二轮验证时这三项超时全部消失。

**根因 B：字段样本造数没写进独特词（脚本缺陷）**

八个字段的搜索全部命中 0 条。`verify-p4.mjs` 造数时只铺开了 `overrides.category` 与 `overrides.tag`，`title` / `url` / `description` / `note` / `selectedText` / `aiPurpose` 六个覆盖项被丢掉——库里根本没有「靛蓝排版」「琥珀装帧」这些词。

修复：八个样本逐字段铺开，每个样本只把独特词写进目标字段、其余字段留空，命中数必须正好 1，多一条就说明索引串了字段。同时补一条用例层单测（`八个字段各自可检索，且不会串到别的字段`），单测 47 → 48。

### 第二轮：9 项失败，其实是同一个根因

第二轮除了八个字段与中文召回，其余全部转绿。剩下的 9 项有个共同点：**都是页面刚打开或刚换关键词时读的数**，而同一个关键词在后面的用例里又能命中。

定位过程：先在 Node 里量索引构建——486 条文档、33.7 万字符，首次构建 + 检索 92ms，后续单次 0.1–0.3ms。所以不是索引慢。再在真实 Chrome 里复现造数流程，打出侧栏「全部收藏」的数量：

| 操作 | 主库实际 | 侧栏显示 |
| --- | --- | --- |
| 造数完成（未重新加载） | 482 条 | 1 条 |
| 只 `page.goto('#home')` | 482 条 | 1 条 |
| 显式 `page.reload()` | 482 条 | 482 条 |

**根因 C：造数后那次「重新加载」根本没有重新加载（脚本缺陷）**

`reloadWorkspace` 用 `page.goto(workspace.html#home)` 想强制重读主库，但地址只有 hash 不同时，浏览器做的是**同文档跳转**：React 不重新挂载，内存里仍是造数前的快照（那一轮只有 1 条模板收藏）。搜索命中是被这份旧快照过滤成 0 的，计数自然「匹配 0 条」；侧栏也一直显示 1 条。后来某个用例点了一次写操作（加入待看）触发 `reload()`，快照才变新，于是同一关键词忽然又有命中——这正是「失败项集中在首屏」的原因。

修复（`scripts/verify-p4.mjs`）：`reloadWorkspace` 在 `goto` 之后补一次 `page.reload()`，真正重读主库；`goto` 加 10 次重试，绕开扩展刚加载时标签页还在初始化的 `Requesting main frame too early`。

**根因 D：换关键词时页面仍挂着上一个词的结果（产品缺陷）**

修好重载后仍有一处会读错：检索是异步的（输入后 120ms 才发起），而 `hits` 在换关键词时没有被清空，页面上短暂显示的还是上一个词的结果与「匹配 N 条」。用户能看到计数跳变，脚本也会读到旧值。

修复（`pages.tsx`）：effect 一进来先 `setHits(null)` 回到「正在检索」，新结果回来再落地。顺带把索引出错的提示从「索引重建失败，请稍后重试」改成带原因的文案——本地索引出错基本都是真实缺陷，藏住原因没有意义。

脚本侧同时把「输入 → 睡 900ms → 读一次」换成轮询到检索落地（`searchSettled` / `settleSearch`），失败时把耗时、是否待定、是否报错、空态、行数、侧栏收藏数、当前页一并记进报告，下次再出问题不用靠猜。
