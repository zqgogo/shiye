# v1b 同步设计评审（2026-10-30）

评审对象：`docs/v1b-sync-design.md` 当前讨论稿。对照当前领域类型、仓储、备份恢复和扩展 manifest，并核对 Cloudflare 官方文档。未修改原稿及用户正在修改的其他文档，未创建或部署云资源。

## 结论

**Workers + D1 可以作为拾页第一个后端，分层和本地优先方向也成立；但目前这份草稿还不是可以直接交付开发的同步契约。** 主要风险来自协议与本地状态机，换成 Node/Postgres 也不会自动消失。

建议保留 Cloudflare 选型，先修正以下语义，再按 S1“单写端、手机只读私有镜像”实施。S2 双向同步应另设验收门槛。

## 1. [P1] 同步不能直接复用“只新增”的备份合并

原稿位置：第 1 节第 4 条（第 11 行）、第 5.3 节。

当前 `packages/storage/src/backup.ts` 的 merge 明确保留本机同 ID 实体：有则跳过；遇到本机活跃实体对应的外来墓碑，也会保留本机活跃状态。这是保守导入的正确规则，但不满足同步。

反例：

- A 把收藏标题从旧标题改成新标题；B 已经有该 ID。按当前恢复合并，B 永远跳过新标题。
- A 删除收藏；B 仍有干净的活跃记录。按当前恢复裁决，B 可能保留活跃实体、忽略墓碑。

建议：复用 URL 校验、隐私规则和派生索引生成等纯规则；单独设计同步合并状态机，至少区分“无本地改动”“有未确认改动”“远端已删除”。干净记录接受新远端版本，有本地改动的保存双方并进入冲突；远端删除不能被当成普通备份旧数据忽略。

表述也应改为“本地库支持离线编辑，云端为跨设备确认状态”，而不是多设备之间仍只有一份本地“唯一主库”。

## 2. [P1] 只排除首次上传不够，缺少“已上传后转本地专用”的撤回协议

原稿位置：第 7 节、验收第 6 条。

反例：普通收藏已经上传，随后用户将其改为 localOnly。如果仅“不进 dirty 队列”，云端旧内容会永久保留，其他设备继续拉取。

需要明确：

- 从未上传的本地专用记录不入上传队列。
- 已上传后转私密，要产生只含必要身份信息的云端撤回操作，并跟踪确认结果；离线时明确显示“本机已设私密，云端撤回待完成”。
- 撤回不能删除本机私密正文，也不能让其他设备的旧副本直接重新上传。
- 默认不上传关联私密收藏的待看，以及可能泄露内容的墓碑标题/网址、策略示例、冲突全文和日志。需要共用同步专用投影白名单，不能直接上传 BackupDocument。
- `conflicts.local/remote` 也可能保留撤回前全文；撤回和保留期必须覆盖这张表。
- 在线云库撤回、其他设备副本、服务商备份保留期是不同范围，不能承诺离线设备立即擦除。

此外，`docs/decisions.md:76` 将“禁止 AI”也写成不上传，而设计第 7 节只排除 localOnly。当前 `privacy.ts` 明确区分 aiBlocked 与 localOnly。应先统一产品含义，不能在不同文档中使用两种隐私承诺。

## 3. [P1] 全局版本分配、epoch 守卫与 CAS 尚未定义为同一原子操作

原稿位置：第 3.1、4、5.1、6 节。

`next_version` 只出现在表结构，SQL 中的 version 全是外部占位符，没有说明如何安全分配。

必须补清：

- version 是每个 library 全局唯一的变更序号，还是每实体 revision？现有 pull 只用 version 作游标，要求前者。不能简单对每条记录 `version+1`：两条记录同版本，分页截断后 `version > cursor` 会漏掉同版本剩余记录。
- 客户端 epoch 校验、版本分配、实体 CAS、必要回执应位于同一数据库事务。只在 Worker 开头读 epoch、随后分开写，会让 reset 与旧请求交错。
- 分配的顺序还应与写入可见顺序相容，防止低序号晚提交、客户端已越过它。迁移 Postgres 时不能直接把“序列产生不同数值”等同于满足此条件。
- `B < S` 的删除优先，与 SQL 的“CAS 不匹配一律 conflict”、以及“后端不做业务裁决”相冲突。可以由客户端读取最新版后显式重试删除，但必须确定这一流程，不能悄悄放宽服务端守卫。
- epoch 不匹配应整请求拒绝；响应示例中逐项 epoch_mismatch 与矩阵的整请求拒绝需要统一。

Cloudflare 的 `batch()` 可以把预备 SQL 放入事务，SQL 失败会回滚整批；它不是可随意在 JS 中读一条再动态追加写入的交互式事务。实现前应提交实际 D1 可执行的 SQL 方案并做并发 POC。CAS 影响 0 行通常不算 SQL 错误，因此允许部分业务冲突与 batch 原子提交可以并存，但必须明确校验错误和真正数据库错误的整批结果。[D1 batch 官方说明](https://developers.cloudflare.com/d1/worker-api/d1-database/)

## 4. [P1] dirty 队列、响应确认与重试幂等仍会留下丢写窗口

原稿位置：第 3.1 节、第 5.3 节、验收第 8 条。

需要把伪代码改成完整持久状态机：

1. **本地实体写入与 outbox 入队在同一 IndexedDB 事务。** 现在“写成功 → 写 dirty”若是两次提交，崩溃时可出现本地已改但永不上传。所有入口都要覆盖，包括弹窗、service worker、批量导入、AI 应用、分类迁移和历史清理。
2. **每次发送保存不可变操作快照。** 例如发送 localRevision=5，等待期间用户编辑到 6；收到第 5 版的确认只能确认对应操作，不能按实体 ID 删除第 6 版的新脏状态。
3. **请求带稳定 opId，响应按 opId 关联。** 现在仅返回 id，无法区分同 ID 的不同 entityType，也无法精确确认同实体多次编辑。
4. **定义成功但响应丢失后的处理。** 仅有 baseVersion CAS，重发已成功的请求会变成 conflict。应使用同事务操作回执/去重，或明确可核对的已应用结果；不能只在验收表写“重试幂等”。旧操作重试不能覆盖别人后续修改。
5. **pull 的数据、冲突保存、同步 shadow 和 cursor 一起提交。** 冲突需先持久化再越过它；再次拉取不应无限重复制造冲突。明确只更新服务端基线，不把确认结果覆盖到用户的新草稿。
6. **允许多上下文时选一个同步执行者。** MV3 worker 退出或页面关闭后可重入；执行租约、重试时间与 outbox 均需持久化，不能仅放在定时器或内存变量里。

## 5. [P1] reset 只有换 epoch，没有定义“云端库替换”的完整过程

原稿位置：第 3.3 节、验收第 5 条。

本地导入旧备份，不应默认等于要求所有设备改用它。如果只修改 libraries.epoch，records 仍然是原云库；后续客户端新初始化会拉回什么、谁负责重新上传、半批上传时手机看到什么，都没有答案。

建议区分：

- **本地恢复**：暂停该设备同步，保留 outbox 与私密数据，让用户选择重新接入当前云库或作为新库上传，不默认影响其他设备。
- **明确替换云库**：高权限操作，携带 expectedEpoch、稳定操作 ID 和待发布的完整数据集；先准备、校验，再原子发布新 generation/epoch。旧请求必须在写事务内被拒绝。
- **服务端数据库回滚/迁移**：恢复到旧数据后，重新开放写入之前处理 epoch，避免旧客户端被误认为仍在当前历史中。

还需补 pull 的 epoch 输入或分页约束：拉完一页后若云库 reset，下一页不能继续沿用旧 cursor。新设备的首次 epoch/library 初始化入口也未定义，三个现有接口并不足以解释首次连接。

## 6. [P1] 实体删除模型与跨实体依赖未统一

原稿位置：第 3.1、4、6 节。

协议同时提供 `entityType: tombstone` 和实体自身 `deleted`，存在两份删除事实；且 tombstone 如何编码原 entityType 未定义。建议云端每个 `(library, entityType, id)` 只保留一份权威状态，`deleted=true` 是该实体的最小墓碑；本地墓碑表只是它的存储映射。

还需要确定：

- 删除记录保留多久；若清理墓碑，旧设备如何识别游标已过期并强制重建。直接删行会破坏不复活保证。
- 删除是否只能由显式 restore 操作撤销。现在 `B=S` 的活跃更新也可能复活删除，是否允许需要定义。
- 同网址不同 ID 的跨设备去重如何保持当前产品语义。
- 分页中收藏先于分类/标签到达，如何暂存引用；不能复用备份的“找不到分类就清空”，否则分类在下一页到达时引用已永久丢失。
- 分类删除并迁移收藏、待看转收藏等本地原子操作，怎样在允许逐项部分成功的 push 中保持可接受状态。应选择依赖顺序、操作组或显式中间态。
- 当前 `purgeCompleted()` 直接物理删除待看、分类删除也没有同步 outbox。实施 v1b 时必须补相应删除事件；BroadcastChannel 广播不能替代持久队列。

## 7. [P1] S1 手机只读必须有服务端权限，不能只靠前端不显示编辑按钮

原稿位置：sessions 表、第 9 节、第 11 节。

鉴权形态可以待选，但权限契约不能全部留空：

- 至少区分只读、写入与云库重置权限；session 目前只有 library_id/expires_at，没有 scope、撤销或设备信息。
- 手机凭据不能调用 push/reset；服务端从认证主体派生 library_id，不信任请求中自行指定的库。
- 所有入口校验类型、字段白名单、字节上限、URL 和非法引用策略。“后端不做业务裁决”不等于不做服务端输入验证和授权。
- 令牌不得进入 URL、公开 HTML、日志、备份或快照；指定获取、过期、撤销及更换服务器后的处理。
- 手机网页需要真正的受保护页面和数据接口，不能直接复用会把个人数据嵌进公开 HTML 的导出模式；私有响应需要明确缓存策略。
- 浏览器 cookie 会话与扩展 Bearer token 的跨域、主机权限和必要 CSRF 方案应分别写清。CORS 不能充当鉴权。

## 8. [P2] S1 只读镜像需要独立的最小契约，现有双向同步接口不能自动替代它

原稿位置：第 9 节。

“一个写端”也可能有多个工作台标签页和扩展收集上下文，并不天然零竞态。应指定唯一发布者/写设备，并在发布端序列化。

建议 S1 使用版本化全量镜像：

1. 桌面从一致本地快照构造同步白名单投影。
2. 分批上传到 staging generation，带条数和完整性校验。
3. 校验完成后原子切换 active generation；中断不替换旧镜像。
4. 手机只读取已发布 generation，搜索可以先在浏览器内完成。
5. 明确取消共享、变私密和重新发布时的撤回行为。

S1 应单列鉴权、上传/发布/读取协议、只读手机页面和验收表。S2 才引入双向 outbox、冲突及 pull 应用；S3 再做字段合并。原稿第 6 节把自动合并写成 S2，与第 9 节 S3 不一致。

## Cloudflare 适配说明

- **选型可行**：Worker 承载 HTTP/鉴权，D1 存状态，手机页面可以用独立静态前端接同一私有 API。核心协议继续只依赖 HTTP/JSON，无需一开始引入 Durable Objects/Queues。
- **50 条是应用批量上限，不是 CPU 安全保证**：免费 Worker 的 HTTP CPU 额度为 10ms，等待数据库不计入 CPU，但 JSON 解析、校验、鉴权与序列化会消耗 CPU。需要同时限制字节数并在真实部署测最坏样本。[Workers 官方限制](https://developers.cloudflare.com/workers/platform/limits/)
- **D1 限制要按当前文档算**：免费单库 500MB，单查询最多 100 个绑定参数，单行/字符串上限 2MB；当前文档明确 `batch()` 对每 invocation 查询额度按一次调用计，不是其中每个 SQL 都各算一次。但各 SQL 自身的参数等上限仍适用，不能把 50 条都塞进一个超参数的大 INSERT。[D1 官方限制](https://developers.cloudflare.com/d1/platform/limits/)
- **不必为了同步强行建完整 changes 表**：唯一、提交有序的全局版本号加保留墓碑，可用 latest-record 表实现最终状态增量；它不提供完整操作审计、严格时点历史或天然的原子全量发布。opId 回执属于重试确认，也不是完整事件流。
- **MVP 可先使用主库读取**：当前 D1 不使用 Sessions API 时查询走主库；若以后启用读副本，要使用 Sessions/bookmark 维护所需一致性，不能拿应用 cursor 当作 D1 bookmark。[D1 读副本说明](https://developers.cloudflare.com/d1/best-practices/read-replication/)
- **费用按访问模式估算**：D1 主要按扫描/写入行数和存储计费，索引会影响行数。应记录最大单条大小、全量大小、更新频率与设备数再估算；不要仅按“收藏条数少”承诺永远免费。[D1 计费说明](https://developers.cloudflare.com/d1/platform/pricing/)
- 国内网络的可达性与实际延迟不能由架构图保证，需要用最终域名、目标网络和手机实测。

## 还需统一的次要契约

- 协议使用 reading，当前领域类型使用 readingItem；明确映射，不在多处暗中转换。
- `AppSettings.libraryId`、本机隐私、localRevision、派生索引、最近打开等不能无选择同步。列出逐实体字段白名单、设备本地字段和版本迁移规则。
- 原稿“备份仍含全量”与当前默认备份排除本地专用不符，应保留“明确勾选才包含”的规则。
- Worker 只引用协议与纯规则；不要因 `packages/sync` 的统一出口间接把 Dexie/客户端实现带入 Worker。协议、客户端、存储端口的导出边界应清楚。
- 换服务器可以保持协议兼容，但还要迁移数据、epoch、身份和凭据，并修改 baseUrl；不同域名可能需要重新请求扩展主机权限。不能承诺只换 worker 文件夹就完成全部迁移。
- 不依赖某厂商专用 header，不代表协议不应使用 Authorization、Content-Type、Cache-Control 等标准 HTTP 头。

## 开工前的最低交付物

1. 选定 S1 或 S2，删除另一阶段暂不实现的模糊承诺。
2. 补一个完整正常流程和五个故障流程：丢响应、本地再次编辑、离线转私密、分页遇 reset、写入中途数据库失败。
3. 给出实际 D1 上可执行的原子版本/epoch/CAS 方案，并用两个并发客户端验证。
4. 固定授权、逐实体白名单、墓碑/撤回语义及本地同步状态表。
5. 增加：已同步记录改名/删除能到达另一设备；已上传后转私密；ACK 不清新改动；push 成功丢响应重试；断点分页与引用；账号 A 不能读写账号 B；只读 token 不能 push/reset；多标签页同时同步。

本次是文档与当前实现的设计评审，不是已部署 Cloudflare 服务的验收。没有新增后端工程，没有运行或宣称通过尚未实现的同步测试。
