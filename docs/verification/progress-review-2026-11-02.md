## 2. 应先修：恢复复用了旧版本号

位置：`packages/storage/src/purge.ts:247–254`。

恢复沿用同一个收藏 ID，却把 `revision` 和 `localRevision` 都设成 1。现有编辑保存的冲突保护只比较 ID 与 `localRevision`，因此会重用一个已经失效的编辑基线。

独立探针已复现：

1. 创建收藏，版本 1；页面 A 持有这个编辑基线。
2. 页面 B 修改标题，版本变为 2。
3. 清空并从清理快照恢复，收藏同 ID、版本退回 1。
4. 页面 A 使用旧基线 1 保存，成功覆盖后来修改的标题，没有版本冲突。

建议作为继续 P9.2 前的 P1 修复：恢复应生成新的写入版本，至少超过快照中原版本，并让恢复前持有的编辑/AI 基线失效；更完整的方案是增加恢复代次或实体代次校验。待看恢复也应按同样的基线失效原则处理。不要只删除版本校验或把旧基线自动改成最新值。同步修订快照设计稿“恢复按新记录版本 1”的规则，并补旧编辑保存及旧 AI 回复的回归。

## 3. 应校正：预览数量并非必然等于执行数量

`previewUndoBatch()` 与 `undoBatch()` 共用判定规则，但二者分别读取数据库，执行只接收 batchId，没有携带预览版本。

独立探针已复现：预览移除 1 条 → 确认前另一页面修改它 → 实际移除 0 条、保留 1 条。执行没有误删被修改记录；这是正确保护，不是要改成照旧删除。

建议：撤回确认说明“执行时复核，期间修改的记录将保留”；执行后显示实际结果，数量变化时明确提示。撤回预览应在只读事务内取一致快照。删除“共用规则所以计数必然一致”的代码注释与进度说明。P9.2 则必须按既定方案冻结候选及版本，防止旧确认扩大作用范围。

## 6. 处理结果（2026-11-02，同日）

### 6.1 恢复复用旧版本号：已修复

复现路径照原样做成正式回归，不再是一次性探针。

| 项 | 处理 |
| --- | --- |
| 根因 | `restorePurgeSnapshot()` 把 `revision` / `localRevision` 写回 1，旧编辑基线与旧 AI 基线重新通过版本校验 |
| 修法 | 硬删除写快照时同时记每条记录的**版本高水位**（`meta` 表 `revfloor:<类型>:<id>`）；恢复时新版本 = `max(高水位, 快照版本) + 1`，收藏与待看都处理。**没有只做「快照版本 + 1」**——从更早的快照恢复时，中间几次编辑的版本可能更高，那样正好撞上旧基线 |
| 回归 | 单测 4 条：旧编辑基线保存被拒且恢复后仍可正常编辑、从更早快照恢复也不退回、待看旧基线不能用于转换、应用层「清理前的材料包不能再写进库」 |
| 文档 | [清理快照与单次恢复](../purge-snapshot-and-restore-design.md) §4 的「按新记录处理、版本 = 1」已改写为现行规则，并写明为什么不能写回旧版本 |

未做「只删版本校验」或「把旧基线自动改成最新值」这类省事做法：前者等于关掉并发保护，后者等于让旧页面以为自己拿到的是最新内容。

### 6.2 预览数量不保证一致：已按「行为正确、表述修正」处理

- `previewUndoBatch()` 改在**同一个只读事务**里读批次、编号映射与每条记录，不再可能读到拼凑的中间状态。
- 删除 `judgeBatchItems()` 里「共用这一套规则，所以不会对不上」的注释，服务层注释同步改写。
- 界面：确认框写明「这是此刻的算法结果，不是承诺：执行时会重新读一遍……」；执行后若与预览有差额，结果面板报出「预览时 X 条，实际移除 Y 条：确认前有 N 条被修改、转过收藏或删除，已按最新状态保留」。
- 执行逻辑没有改成「照预览删」——预览后被改动的条目仍然保留，这正是要保住的并发保护。
- 记录进 [open-issues](../open-issues.md) ⑫，并写明「处理全部匹配」不沿用这个口径：它冻结候选与版本。
