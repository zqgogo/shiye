## 给执行 AI 的工作方式

1. 先检查 Git 分支、工作区改动和适用的 `AGENTS.md`；阅读本规划、目标阶段和相关技术说明。保留已有改动。
2. 从当前阶段第一个未完成的任务开始。一次处理一个可验证的小任务；完成后记录改动、实际验证命令或操作、结果、风险和下一项。只按用户授权的范围继续。
3. 使用脱敏数据和 fixture。不要读取用户真实收藏、接入真实密钥或部署云资源，除非用户明确提供并授权。需要设备、供应商或凭据的验证明确记录为待验证。
4. 不能把构建成功、模拟结果、桌面缩窗或静态检查当作真实浏览器、手机或服务商验证。失败要保留证据并修复或记录阻塞原因。
5. 若资料冲突，产品与技术实现说明优先作为需求依据；记录冲突和决定。技术说明第 22 节采用 P0–P6 的合并编号，任务书细分为 P0–P7：本规划采用后者，P4–P5 对应技术说明 P4，P6 对应技术说明 P5，P7 对应技术说明 P6；任务范围不因此删减。
6. 扩展是唯一可编辑主库的入口；普通网页不能被默认为与扩展共享 IndexedDB。AI 默认关闭，手动交接和内置通道共用隐私、授权、校验和事务规则。v1b 单独安排。
7. 接手时确认资料包可读。若只拿到 Git 仓库而没有同级 `resource`，先取得需求资料，不能凭任务标题推测字段或协议。资料包正文中的部分配套文件名仍写 v2_0，本目录实际提供 v2_1，读取实际文件并记录该文案差异。
8. 任务勾选表示该任务的实现与验收均完成。外部设备或凭据暂不可用时，记录具体阻塞任务，继续不依赖它的已授权工作；不得把整个阶段标完成。阶段状态为阻塞时，也要注明可继续的独立任务。

目标：确认后续实现的基础可行，并形成可重复的开发环境。结果填写 [P0.md](P0.md)。

- [x] **P0.1 工程准备**：检查 Node 版本及项目结构，选定兼容的 React、TypeScript、Vite、Dexie 等依赖与测试工具，加入锁文件和最小构建、类型检查、测试命令；记录运行要求。只搭最小验证入口。
- [x] **P0.2 扩展与主库**：搭建最小 MV3 扩展、popup 和工作台，验证它们在同一扩展 origin 访问同一 IndexedDB 主库；记录 Chrome / Edge 版本、加载方式及主库位置。
- [x] **P0.3 重启验证**：写入脱敏样例，关闭并重开浏览器及扩展后读取；记录实际步骤、结果与限制，验证 MV3 生命周期相关假设。
- [x] **P0.4 文件与手机验证**：用脱敏多层书签 HTML 和损坏输入验证文件读取及层级解析方案；验证最小手机只读 HTML 的可打开性。记录实际设备和浏览器；设备不可用时保留待验证项。
- [x] **P0.5 结论**：记录通过、失败、未测、调整和后续方案。供应商真实请求在用户选择供应商并授权凭据后验证；没有凭据时独立列为待验证，不阻塞与其无关的本地基础工作。

## P1 · 核心规则、数据模型与持久仓库

- [x] **P1.1 领域模型**：按技术说明及 `reference/domain.ts` 建立正式类型与运行时校验，覆盖待看、收藏、分类、标签、设置、批次、日志和墓碑；移除价值等级及其理由。
- [x] **P1.2 纯规则**：实现保守 URL 规范化、字段授权、隐私过滤和版本规则；区分 `originalUrl` 与 `canonicalUrl`。
- [x] **P1.3 持久化**：设计并实现 Dexie schema、索引、迁移与 Repository；通过 application 用例访问数据，避免 UI 直接操作数据库。
- [x] **P1.4 事务与验证**：覆盖重复创建、版本冲突、事务回滚、未分类索引、旧数据迁移与关闭重开；索引及授权不能依赖不适用的 boolean/null 键或宽泛的 `Partial`。
- [x] **P1.5 数据保护基础**：集中字段和容量限制，校验文件、消息、AI 输入而不仅是 TypeScript 类型；按技术说明定义旧格式迁移及默认未读规则。当前没有生产旧库，使用有版本说明的 fixture 演练。迁移前须具备最低可恢复备份能力；迁移失败停止编辑并保留原库，不通过删库重建掩盖错误。
- [x] **P1.6 并发与删除规则**：用多窗口并发验证事务内 URL 去重、稳定 ID、版本比较和墓碑；明确软删除、显式恢复、正文清理及最小墓碑保留规则。网络、文件解析和 hash 计算放在事务外，派生搜索索引可重建。

完成证据：可复现测试覆盖上述失败路径与数据完整性，迁移结果和浏览器重启验证有记录。

## P2 · 工作台、待看与收藏

- [x] **P2.1 页面骨架**：依据设计稿实现暖白、绿色和分组导航，以及首页、待看、收件箱、未分类、全部收藏、最近打开、详情、回收站的基础页面。

- [x] **P2.3 状态与详情**：实现收藏编辑、取消、锁定、隐私、版本保护与最近打开 15 条；未读与分类状态独立，打开、分类或 AI 处理不自动标已读。
- [x] **P2.4 页面验证**：验证已分类未读、未分类已读、已有收藏加入待看、完成撤销、空状态、长标题与失败提示。

背景：一次导入几百到上千条时，逐条勾选不成立。优先顺序是**退这次导入 → 清这批的一部分 → 清空一个明确范围**，通用条件面板是补充而不是入口。需求与场景见 [导入撤回与批量清理：场景与设计说明](import-rollback-and-bulk-cleanup-design.md)，分层与接口见 [按条件清理设计讨论稿 v0.2](purge-by-criteria-design.md)。

**已有基础功能已完成**：HTML 默认导入收藏库、原目录映射到已有分类、结果页及最近批次撤销、清空 pending 待看、清空全部收藏/指定分类/未分类。下列 P9.1–P9.5 是这些功能的增强任务，不能因它们未完成而把已有功能记为未实现。当前没有按站点/原始目录/关键词组合清空匹配集，也没有清空后的一键恢复。专项核查见 [导入与清理复核](verification/import-cleanup-review-2026-10-31.md)。

- [x] **P9.0 修范围计数**：已修复分类/未分类页确认数遗漏回收站的问题，清空前拆出"正常 N · 回收站 M · 删除标记 K"。单测与 Chrome 页面核查通过，证据见上述专项复核。
- [x] **P9.4 清理快照与单次恢复（提前到最前，用户已确认）**：设计与验收见 [清理快照与单次清理恢复](purge-snapshot-and-restore-design.md)。四条硬性要求：
  1. **保护范围**：全部收藏 / 分类 / 未分类 / 清空待看 / 清理完成历史 / 撤销导入，共 6 个硬删除入口都必须在同一 `rw` 事务内先写 `purgeSnapshots`（算候选 → 写快照 → 删除 → 记数），任一步失败整体回滚。软删除与移除单条待看不存快照。
  2. **恢复入口同批交付**：只加回该份快照删掉的条目，不调用整库替换、不 `clear` 任何表；冲突默认跳过不覆盖（同 ID 在库 / 同 ID 在回收站 / 同网址已重导入 / 分类已删落未分类 / 网址命中墓碑时清墓碑重建），执行前事务内复核，预览后被改动的不静默纳入。
  3. **容量与失败**：保留最近 **5 份**、单份上限 **5000 条或 5 MB**、总量 **50 MB**；快照写不进去（空间不足/配额超限）**立即中止，一条都不删**；删除阶段失败整体回滚且不留半份快照；替换恢复不得清掉 `purgeSnapshots`。
  4. **测试**：单测覆盖快照失败、删除中途失败、单份超限、并发改动的冲突矩阵；`verify:p3` 覆盖六入口留痕、恢复不改动其它记录、淘汰到 5 份、重开浏览器后仍可恢复。
