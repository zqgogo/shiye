# 按条件清理：设计讨论稿

版本：0.1。日期：2026-10-30。**未立项、未写码**，本文只用于评估形态与取舍。

## 0. 一句话

不是"勾选几条删几条"，而是"说清你要清哪一类，界面告诉你命中多少条，你确认后一次清掉"。

## 1. 为什么勾选不成立

一次导入 300～2000 条时，逐条勾选的成本高于手动重导。真正的诉求是**用一个条件概括"这一坨我不要"**，例如"上周从「工作/待读」目录导进来的、我一次都没打开过的"。

所以清理的单位不是条目，是**条件命中的集合**。

## 2. 现状：已有的五档（都保留）

| 入口 | 粒度 | 可恢复性 |
| --- | --- | --- |
| 数据页 → 最近导入 → 撤销这次导入 | 一批里"没被改过"的 | 硬删，不可撤销（为的是能重导） |
| 收藏 → 分类页 → 彻底清空 | 单个分类下的收藏 | 硬删 |
| 收藏 → 未分类 → 彻底清空 | 无分类的收藏 | 硬删 |
| 收藏 → 全部 → 彻底清空 | 整库 | 硬删 |
| 待看 → 清空待看 | 全部待看 | 硬删 |

缺口很明确：**上面五档只能按"整批 / 整类 / 整库"切，切不出"这一类"**。而用户实际想清掉的往往横跨分类，只由几个属性定义。

## 3. 三个候选形态

| 方案 | 形态 | 优点 | 代价 |
| --- | --- | --- | --- |
| A 条件面板 | 6～8 个条件叠加，实时显示命中数 | 表达力最强，能精确到"没动过的" | 条件多时理解成本高；要造一个新页面区块 |
| B 一键卡片 | 三张卡：刚导入没动的 / 某个目录的 / 某个站点的 | 点两下就完事 | 表达力受限，新场景要加卡 |
| C A+B | 卡片给常用路径，面板给兜底 | 兼顾 | 实现多一层，需要控制不重复 |

**推荐 C，但分两期**：第一期只做 A 的条件面板（B 的三张卡本质是 A 的预设，后面加成本很低）；等看到你实际怎么用，再决定把哪几个组合固化成卡片。

## 4. 推荐方案

### 4.1 条件维度

前提：条件之间是**与**关系，留空即不限。默认值选"最安全的一侧"——不勾任何"会扩大命中"的条件。

| 维度 | 取值来源 | 适用 | 说明 |
| --- | --- | --- | --- |
| 范围 | 收藏库 / 待看 / 两者 | 两者 | 默认"收藏库" |
| 批次 | `importBatches` 最近 20 批 → `sources[].importBatchId` | 两者 | 用来"再撤一次导入"，但可叠加其它条件缩小 |
| 原始目录 | `sources[].originalFolder` 去重 | 两者 | 导入收藏夹时保留的 Chrome 文件夹名，如「工作/待读」 |
| 站点 | `canonicalUrl` 的主机名，按条数倒序 | 两者 | 单个站刷出 800 条时最快 |
| 导入时间早于 | `createdAt` / `addedAt` + N 天 | 两者 | 用于"三个月前囤的" |
| 从没打开过 | `lastOpenedAt === null` | **仅收藏** | 待看没有"打开"这个概念，用它没有意义 |
| 没有分类 | `categoryId === null` | **仅收藏** | 待看没有分类字段 |
| 没有标签 | `tagIds.length === 0` | **仅收藏** | 同上 |
| 没有备注和摘录 | `note === '' && selectedText === ''` | **仅收藏** | 比"没分类"更接近"完全没加工" |
| 已在回收站 | `deletedAt !== null` | 仅收藏 | 只清已经删过的，连带清墓碑 |

**不对称要写在界面上**：待看只支持范围、批次、目录、站点、时间五项；收藏相关的四项在选"待看"时置灰并说明原因，不做假开关。

### 4.2 动作分两档

| 动作 | 收藏 | 待看 | 语义 |
| --- | --- | --- | --- |
| 移入回收站 | 软删（`deletedAt`，留墓碑） | **没有回收站，等同删除** | 可恢复，适合"先清一批看看" |
| 彻底删除 | 硬删 + 清墓碑 | 硬删 | 用于"清空后重导"，不可恢复 |

待看没有回收站这件事是现存边界，面板上必须直说，不能让人以为能捞回来。

### 4.3 界面线框

放在**数据与备份**页，「最近导入」下方。理由：危险动作集中在一处，不干扰日常浏览。

```text
按条件清理
清掉的是一类，不是几条。左侧条件叠加，下方实时显示命中多少条。

范围    (•) 收藏库   ( ) 待看   ( ) 两者
来源    批次 [最近 20 批 ▾]   原始目录 [全部 ▾]   站点 [全部 ▾]
状态    [ ] 从没打开过   [ ] 没有分类   [ ] 没有标签   [ ] 没有备注和摘录
时间    [ ] 导入早于 [ 30 ] 天

── 命中 231 条（收藏 180 · 待看 51）
   其中 12 条有备注或已分类，6 条有标签
   预览 · 某某文档 - a.com
        某某文档 - b.com   还有 229 条

[ 移入回收站 231 条 ]   [ 彻底删除… ]
```

### 4.4 交互细节

1. **没有任何条件时按钮禁用**，并提示"至少选一个条件"——否则就是一键清库，必须堵死。
2. **命中数实时算**，条件改动即时刷新；数据量大时用 150ms 防抖，避免每次按键都过滤全库。
3. **命中 0 条**时按钮禁用，文案改成"没有符合条件的条目"。
4. **执行前二次确认**，确认框里复述条件（不是只写"确定吗"），并要求看到命中数与"其中 N 条已加工"的提示。
5. **执行时按条件重算，不按预览的 id 列表删**，见 5.3。
6. **执行后如实报数**："移除 229 条，12 条因导入后被改过而保留"。与预览不一致时必须说明原因，不能静默。
7. **彻底删除**在确认框里额外要求勾选一句"我了解这些条目和删除标记都会消失，之后用旧备份可能被带回"。

## 5. 数据与实现

### 5.1 单一谓词，三个调用方

```
packages/core/src/purge.ts          matchesPurgeCriteria(record, criteria)  ← 纯函数
        ↑ 前端预览（内存里已加载的全量数据）
        ↑ storage.previewPurge(criteria)（只读，事务外）
        ↑ storage.purgeByCriteria(criteria)（事务内重算再删）
```

**必须是同一个函数**。预览与执行各写一套判断，是这类功能最典型的翻车方式——预览说 231，实际删了 260。

### 5.2 接口签名（示意）

```ts
export interface PurgeCriteria {
  scope: 'library' | 'reading' | 'both';
  batchId?: Id;
  originalFolder?: string;
  host?: string;
  olderThanDays?: number;
  neverOpened?: boolean;
  uncategorized?: boolean;
  untagged?: boolean;
  bare?: boolean;        // 无备注且无摘录
  includeTrash?: boolean;
}

previewPurge(criteria): Promise<{ bookmarks: number; reading: number; touched: number; sample: { id: Id; title: string }[] }>;
purgeByCriteria(criteria, mode: 'trash' | 'hard'): Promise<{ removed: number; trashed: number; kept: number }>;
```

### 5.3 执行时重算

预览到执行之间有窗口期（几十秒到几分钟），期间可能又导入了东西或改过某条。所以 `purgeByCriteria` **接收条件而不是 id 列表**，在同一个读写事务里重新跑谓词，删掉的那一刻才算数。

返回 `kept`（因 `localRevision > 1` 保留）：与「撤销导入」同一条判据——**用户之后做过的决定不该被一次清理抹掉**。

### 5.4 与「撤销导入」的分工

「撤销导入」= `batchId=最近一批 + 未加工 + hard` 的一个特例。保留它，因为它是"我刚导错了"的最短路径（一个按钮）。但底层改成调用同一个谓词，避免两套语义。

`undoBatch` 额外要做的事（批次状态记 `reverted`、清墓碑）保持在仓库层，不进谓词。

### 5.5 性能

- 工作台已把收藏与待看全量载入内存，10k 条以内线性过滤是毫秒级，预览不必查库。
- 真正删的时候单事务 `bulkDelete`。10k 条在 IndexedDB 单事务里约几十毫秒，可接受；超过 20k 再考虑分块，但分块会带来"部分成功"，届时必须配断点续做，不急着现在做。

## 6. 风险与代价

| 风险 | 缓解 |
| --- | --- |
| 误删已加工内容 | 默认不勾"扩大命中"的条件；预览单列"其中 N 条已加工"；执行时 `localRevision > 1` 强制保留 |
| 硬删不可恢复 | 默认动作是"移入回收站"；彻底删除要额外勾确认 |
| 清墓碑后旧备份被带回 | 与 open-issues ⑨ 同一代价，确认框内原文复述 |
| 条件理解成本高 | 条件带一句话说明 + 命中预览让人先看到后果 |
| 待看无回收站 | 面板直说，不提供假的"可恢复"暗示 |
| 与 v1b 同步的交互 | 将来清理也要产出 delete 操作进 outbox；本期不涉及，谓词设计成不依赖同步层即可 |

## 7. 验收与测试

**单测**（`packages/application`）

1. 只选范围 + 无分类，只命中无分类的收藏
2. `localRevision > 1` 的条目保留并计入 `kept`
3. 批次 + 从未打开 叠加时取交集
4. 待看范围下，收藏专属条件被忽略而不是报错
5. 空条件被拒绝（`INVALID_INPUT`）
6. `hard` 模式连同墓碑一起清，之后同网址可重导
7. `trash` 模式保留墓碑，回收站里能看到
8. 预览与执行计数一致（同一份数据、无并发）

**浏览器断言**（`verify:p3` 追加约 6 条）

9. 无条件下按钮禁用
10. 选一个空分类后命中 0、按钮禁用
11. 命中数与列表实际条数一致
12. 执行后报数与预览一致
13. 彻底删除后 `imports` 同批可重导
14. 移入回收站后条目出现在回收站、不在收藏列表

**手册**：新增一节 B 组用例（约 3 分钟），含"故意选错条件后取消"。

## 9. 待你决定

1. **默认动作**：移入回收站（可恢复、但收藏会进回收站占位）还是彻底删除（干净、但不可恢复）？我倾向回收站。
2. **待看要不要也做回收站**？现在待看删除即消失，只有备份能救。加软删字段要做迁移，工程量不小；不加就得在界面上接受"待看删了就是删了"。
3. **清理前自动导出一份 JSON** 默认开还是关？开了更安全，但每次清理都多一个下载文件。
4. **面板放数据页**可以吗？还是你希望它就在收藏/待看列表页顶上（看得见、但危险动作离日常操作更近）。
